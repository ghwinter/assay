# AI 软件工程工作流 v0.2

> 目标：把人的产品意图整理成可裁决的工程决定、局部模型、AI 工作包和可复跑证据。
> 本流程不承诺“AI 已知代码绝对正确”；它要求每项重要主张有适用范围、假设和判定方式，
> 并让未判定的部分保持可见。
> 生命周期框架适用于不同技术栈；Rust 模板只是一个具体起步后端。

## 分层职责

| 层 | 负责什么 | 主要产物 |
|---|---|---|
| Spec Ledger | 项目为什么存在、目标、开放问题、决定、假设、义务 | `G-*.yaml`、`D-*.yaml`、义务与证据 |
| 工程前端 | 把一个获准的变化组织成边界清楚的任务；列出模型、接口、约束和待裁决项 | `engineering/` 文档、AI 工作包 |
| 项目后端 | 对特定主张建模、实现和判定 | Rust 代码、Quint/TLA+、Verus、结构检查、测试 |
| Assay | 执行项目登记的检查，记录证据，检查清单和棘轮 | `assay/evidence/`、`assay/MAP.md`、`assay/ratchet.toml` |
| 人 | 确认意图、接受取舍与风险、处理冲突和未知 | 已裁决的目标与决定、签名的风险接受 |

工程前端不是把自然语言自动翻译成真规格的编译器。AI 可以起草模型和决定，
但人必须确认模型表达的行为确实是要做的事；验证器只判断它被委派的主张。

## 项目生命周期与人机分工

项目规模越大，增加的应是责任、评审和证据的清晰度，不是每个阶段都多写一份文档。
小项目可以把多个产物合并；企业和开源项目则需要显式的责任人、提案/评审路径、变更记录与发布责任。
无论规模如何，都要区分：人裁决“应该是什么”，AI 提出与整理候选，确定性工具判定声明范围内的结果。

| 阶段 | 人类裁决/讨论 | AI 可辅助/生成 | 可确定性自动化 | 典型产物 |
|---|---|---|---|---|
| 目的与范围 | 解决谁的什么问题；成功、失败代价、非目标与风险容忍度 | 访谈提纲、摘要、冲突和缺失项提示 | 必填项、ID、格式等完整性检查 | 产品简述、目标、开放问题 |
| 需求与验收 | 在利益相关者冲突时取舍；接受业务、安全、合规风险 | 起草需求和验收条件；标记矛盾、覆盖缺口 | 结构校验、链接有效性、已声明覆盖规则 | 需求、约束、假设、验收标准 |
| 架构与分工 | 选择边界、数据/接口所有权、关键取舍、负责人和依赖顺序 | 比较候选架构、整理影响面、起草 RFC/ADR 和任务拆分 | API 兼容性、依赖边界和架构规则检查 | 架构决定、接口契约、责任分配 |
| 正确性策略 | 决定哪些性质承重、需要何种置信度，以及何时必须阻断发布 | 将决定展开为候选义务；建议模型、检查器和覆盖矩阵 | 按声明执行测试、模型检查、证明与安全策略门禁 | 义务、验证计划、模型与检查映射 |
| 实现与评审 | 评审意图是否保持、接受有争议的行为变化；按项目规则批准合并 | 在授权范围内实现；总结差异和未覆盖项 | 格式化、构建、静态检查、测试、证据归档 | 工作包、代码变更、评审记录、检查结果 |
| 发布与部署 | 对未消除的风险作发布决定；选择灰度和回滚策略 | 整理变更和风险摘要、起草发布说明 | 可复现构建、制品签名、SBOM、部署门禁、健康检查与自动回滚 | 版本、构建来源、发布决定、部署记录 |
| 运行与事故处理 | 判断严重度、优先级、用户影响和对外承诺；决定恢复策略 | 整理事故时间线、提出根因假设和复现步骤 | 指标/日志/追踪、告警关联、故障回放、满足策略时自动回滚 | 运行证据、事故记录、修复与新增义务 |
| 演进与治理 | 企业变更审批、开源维护者决策、兼容性和路线取舍 | 变更影响候选、过期证据提示、发布说明草稿 | 标签/规则校验、声明的证据新鲜度与发布门禁 | RFC/ADR 更新、迁移计划、弃用与版本策略 |

CI/CD 适合反复、可判定、能给出稳定结果的检查；它不能替团队决定产品价值、优先级、规范含义或风险接受。
AI 可以辅助这些讨论，但提案、摘要或自动生成的模型都不是批准本身。开源项目可用 RFC、maintainer review
和明确的测试/审阅记录表达治理；企业项目可增加职责分离、合规审批和发布授权。具体形式可不同，决定必须可追溯。

## 中间产物：不同语义，不重复抄写

目标到代码不是一条把所有内容都编译成代码的流水线，而是一组有类型、有责任边界的转换与反馈：

```text
目的/需求 → 架构与行为模型 → 契约/义务 → 实现 → 构建制品 → 部署与运行证据
    └────────────────────── 变化、反例、事故反馈 ──────────────────────┘
```

| 产物类别 | 它回答的问题 | 示例与职责 |
|---|---|---|
| 意图/决策 | 为什么做、选了什么、哪些仍未知？ | 目标、需求、假设、RFC/ADR；由有权的人裁决，AI 可起草 |
| 结构模型 | 谁负责什么，组件/接口如何分配？ | 架构图、接口契约；复杂到人工难以核对时才用 MBSE/Capella |
| 行为模型 | 状态、并发、时序、失败路径允许什么？ | Quint/TLA+ 描述所选协议/状态机及性质，不自动证明实现符合模型 |
| 实现契约 | 核心函数在什么前提下保持哪些不变量？ | Rust 类型、前后置条件与 Verus；证明只覆盖声明的契约、范围和假设 |
| 可执行控制 | 怎样重复执行门禁、构建和部署？ | CI/CD、构建配置、策略即代码；配置也是需审阅和版本控制的工程产物 |
| 实现与制品 | 实际交付了什么？ | 源码、生成代码、二进制、容器；生成物应记录来源和生成器版本 |
| 证据与来源 | 哪个检查对哪个版本、范围和假设得出了什么结果？ | 测试结果、模型反例/通过记录、证明结果、基准、SBOM、签名与构建来源；彼此不能混作同一种“证明” |
| 派生视图/工作包 | 当前获准内容如何交给人或 AI 执行？ | AI 工作包、依赖地图、验证矩阵；由权威来源生成，不再手工维护第二份权威声明 |

每个产物都应“承担租金”：约束下游、触发义务、减少关键不确定性或提供可审证据；做不到就合并或删除。
跨层关联也应标明含义，例如“分解为”“分配给”“细化为”“实现”“由……检查”“由……构建”“由……观测”，
不要把所有链接都叫作追溯或证明。每次转换应留下其工具/版本、输入、假设和结果；尤其要审查模型到实现的对应关系。

## 按需借鉴参考项目

`D:\GitHub` 是本机可检索的工程参考库，不是需要预先读完的课程，也不是本项目的规格来源。
只有遇到一个具体的不确定问题时才检索，例如“多次并发执行怎样安全追加证据”或“这个协议性质应怎样抽象”。

1. 先把问题和本地约束写成一句话，再只选少量相关仓库；用 `rg --files` / `rg -n` 查目录、文档、实现和测试，不做全库通读。
2. 围绕同一个行为读一条最小纵切：设计说明或 README、实现位置、相关测试/示例；需要理解缘由时再查历史或 issue。
3. 提取机制、它解决的问题、成立的前提、失败边界和不适用于本项目的部分。借鉴设计，不盲目复制代码；复制/改编代码前另行审查许可证和署名要求。
4. 影响产品行为或架构时，把裁决写入 Spec Ledger 的 `D`，把可判定要求写成 `O`；参考笔记只记调研，不成为第二份规格。
5. 记录仓库 URL 或本机路径、精确 revision、文件/符号、观察到的模式、采用/改写/拒绝的理由，以及本项目的验证方式。低影响的一次性实现细节可直接在代码评审中说明，不必制造一篇新文档。

在 Windows 上可将根目录设为 `$referenceRoot = 'D:\GitHub'`，例如：

```powershell
$repo = Join-Path $referenceRoot 'codex'
rg -n -i 'jsonl|append_payload|write_all' (Join-Path $repo 'codex-rs\analytics\src') -g '*.rs'
git -C $repo rev-parse HEAD
```

本次工作以 Codex 的 JSONL 追加实现和多行测试，校验 Assay 的证据写入方式；
Quint 的模型审查指南则提供了“结构审查 + 运行检查”并严格限制结论范围的例子。
这些参考只解释为什么选择某种工程做法，不替本项目的人类裁决或本地检查结果背书。
若调研值得保留，可从 `templates/rust-app/engineering/REFERENCE_NOTE_TEMPLATE.md` 起草一份短笔记。

## 初始化

在 Assay 仓库根目录运行：

```powershell
pwsh -NoProfile -File tools/new-rust-project.ps1 `
  -Target D:\work\my-rust-app `
  -Name my-rust-app
```

脚本调用本仓库内的 `spec.py init`，再复制 `engineering/` 模板和空的
`assay/manifest.toml`。它不会选择 GUI、Web 框架、数据库或系统架构，也不会替人写目标。
随后填写 `engineering/INTENT.md`，由 AI 起草目标，人确认后再开始第一条纵切。

如果不使用脚本，等价操作是从本仓库根目录运行：

```powershell
python tools/spec.py init D:\work\my-rust-app my-rust-app
```

然后把本仓库 `templates/rust-app/engineering/` 复制到新项目的 `engineering/`，
把 `templates/rust-app/assay/manifest.toml` 复制到新项目的 `assay/manifest.toml`。

## 一条功能纵切

### 1. 说清目的与验收

填写 `engineering/INTENT.md`。先描述用户、使用场景、外部系统、成功条件、失败后果、
运行环境和非目标。AI 先提澄清问题、列出假设和冲突，不要把未回答的问题偷偷变成设计。

每个目标写成可观察的结果。数字阈值必须说明使用场景和来源；没有来源的阈值标为
`synthetic`，不能伪装成产品需求。

### 2. 决定一个端到端路径

先选一条最小但真实的纵切，例如一次用户操作从入口经过应用逻辑、领域规则、持久化或
外部服务，再返回可观察结果。用 `engineering/ARCHITECTURE.md` 写明实际的边界和数据流。

至少回答：

- 谁拥有每份状态；哪些状态会持久化；写入何时算成功？
- 哪些调用同步或异步；取消、超时、重试、重复请求和部分失败如何处理？
- 身份、权限、敏感数据和外部服务凭据在哪一层处理？
- 启动、配置、健康检查、关停、升级、迁移、恢复和回滚分别怎么工作？
- 关键边界的输入、输出、错误语义和可观察证据是什么？

不要预先规定完整模块树。先确定端到端路径、职责和可验证接口；模块边界可以随真实变化
修订，修订要回写决定和受影响的义务。

### 3. 形成决定并展开义务

AI 根据目标和架构草拟 `D-*.yaml`，列出备选、理由、假设、开放问题和受影响产物。
人裁决影响产品行为、数据语义、权限、安全、兼容性或不可逆成本的选择。未裁决问题保留
为 `open_questions`，不得由 AI 静默选定。

对每条决定运行：

```powershell
python tools/spec.py expand D-001
```

把相关触发器产生的义务逐条审阅后并入决定；展开结果是候选，不是自动接受的规格。
每条义务应回答：它约束什么、违反意味着什么、范围与假设是什么、用哪种判定器检查。

### 4. 按主张选择后端

选工具看“哪条义务缺少足够判定”，不要以工具清单决定架构。低成本手段足够时不升级。

| 主张类型 | 首选判定方式 | 何时升级 |
|---|---|---|
| Rust 语法、所有权、类型与常见静态错误 | `cargo check`、`cargo clippy`、类型系统 | 不以形式化工具重复证明编译器已判定的性质 |
| 模块依赖、接口和分层规则 | 依赖检查、API/结构测试 | 跨系统分配和接口关系复杂到难以人工核对时，考虑 MBSE/Capella |
| 并发、协议、状态机、超时与活性 | 状态模型与性质测试 | 交错空间承重时使用 Quint/TLA+ 模型检查；若要验证真实实现，还需轨迹驱动与状态投影 |
| 纯 Rust 核心的数据不变量与前后置条件 | 单元/属性测试 | 核心性质后果严重且契约可审时，使用 Verus |
| 持久化、崩溃恢复和迁移 | 集成测试、故障注入、恢复/对拍 | 存在多阶段状态协议时，再增加模型检查 |
| 性能、资源和可用性预算 | 基准、剖析、运行监控 | 预算必须绑定明确负载、硬件和测量方法 |

Capella/MBSE 负责结构分解、分配与接口完整性，不证明行为或 Rust 实现正确。
Quint/TLA+ 模型通过不自动证明真实实现符合模型；需要可审的模型到实现映射和实现轨迹检查。
Verus 证明的是给定契约下的实现性质，不证明契约符合用户意图。

### 按变化动作路由，而不是按工具清单堆叠

对每个变化先问：用户可观察行为改了什么、可能破坏哪条义务、哪个判定器能发现它？一个变化可以产生多条义务，
也可以只用一条廉价的检查；不要求每个功能都同时写 MBSE、TLA+ 和 Verus。

```text
变化/动作 → 受影响的行为 → 候选义务 → 适配的判定器 → 带范围与假设的证据 → 通过、修复或人工裁决
```

例如新增后台任务，不是笼统地要求“做 TLA+”，而是拆成队列状态与并发交错、取消和关停、重试/幂等、
错误传播、资源上限和可观测性等问题。状态协议若存在高风险交错，可由 Quint/TLA+ 检查模型；
纯函数不变量可用测试或 Verus；关停、崩溃和外部服务行为用集成/故障注入测试；日志和追踪检查诊断能力。
人仍需确认这些义务是否覆盖真实需求、模型假设是否成立，以及哪些残余风险可接受。

Debugger 属于诊断/调查工具：它帮助定位偏差、收集状态并形成可复现用例，不单独证明正确性。
一次调试的有价值结果应回流为修复、回归检查、模型反例或新义务；否则同类故障仍可能再次发生。

每个新检查先故意注入一次被禁止的情况，确认它能失败、失败可定位，再把命令登记到
Assay manifest。对于工具返回码不能代表判定结果的情况，必须用项目 wrapper 解析报告，
并让 wrapper 自己也有负例检查。

### 5. 给 AI 发工作包

每个 AI 实现任务先从已接受的决定生成一份结构化工作包：

```powershell
python tools/prepare_work_package.py D-001 `
  --root . `
  --output engineering/work-packages/D-001.md
```

生成器只读取已接受且未被取代的决定、关联目标、假设、义务、检查器与工件路径；它不猜测
影响面、不更改账本、不把历史 `pass` 当作当前证据。然后按
`engineering/AI_WORK_PACKAGE.md` 补上本次具体授权范围、基线提交和禁止变更项。工作包至少包含：

- 目标与验收条件，以及关联的 `G`、`D`、义务 ID；
- 已裁决的行为、接口、所有权、失败语义和不能自行改变的边界；
- 涉及的规格/模型/代码文件和预期产物；
- 必须运行的检查命令、证据位置和完成条件；
- 所有未解决问题、假设和不覆盖的性质。

AI 可以修改工作包明确授权的产物。发现目标或决定不完整时，先提交修改提案并暂停依赖它的
实现；不得通过改模型或删检查让代码变绿。完成时，AI 报告实际运行的命令、结果、反例、
未判定项和偏离计划之处。

### 6. 运行检查并保存证据

Spec Ledger 的检查入口：

```powershell
python tools/spec.py check O-001
python tools/spec.py check --type test
```

Assay 用于独立项目清单的检查、证据落盘与棘轮：

```powershell
assay map --root .
assay check --root .
assay run --root . --change CH-001
```

若尚未安装 `assay` 可执行文件，可从本仓库用 `cargo run --manifest-path
<assay-root>\engine\Cargo.toml -- <子命令>` 调用。Spec Ledger CLI、账本工具与 Assay
引擎现位于同一仓库；新项目会复制一份可独立运行的 Spec Ledger 工具链，并保留自己的
Assay 清单。当前 Spec Ledger 与 Assay 之间尚无
自动清单转换；v0.6 的 claim→obligation 源链接仍需显式审阅，不能由引擎猜测。工作包生成器
会按义务 ID 读取最新 Assay JSONL 记录，并把它标成历史证据；仅在没有新事件时回退到旧的
`ledger/evidence/O-*.yaml`。回退数据不与新事件构成双重权威。

每条证据要能追溯到确切产物和检查器版本、检查范围及假设。结果至少区分 `pass`、`fail`、
`skip`、`unknown` 和过期；跳过、失败或缺失都不能显示成通过。变化后重跑所有受影响检查；
范围不明时标为未知并升级给人。

检查器输出会进入证据明细；wrapper 必须限制摘要长度并脱敏，绝不输出密钥、令牌或个人数据。
Assay 不理解也不自动清洗后端输出，证据目录的访问和保留策略由项目负责。

### 7. 提交与发布

提交前完成项目定义的本地门禁；CI 再复跑承重检查。发布检查覆盖构建产物来源、包内文件、
安装/启动、配置与权限、升级/迁移、失败恢复和回滚。运行时检查负责证明模型没有覆盖的
环境性质；正式运行证据不能拿单元测试替代。

允许发布的条件是：所有标为发布必需的主张都有当前且范围匹配的证据，假设仍成立，未知项已
由责任人接受或阻断，产物来源可追溯。结论只适用于这些主张、范围和环境，不宣称“整个程序
已被证明正确”。

## 日常回路

```text
意图/变化
  → 提问与假设
  → 人裁决关键选择
  → 义务展开
  → 选择最便宜且足够的判定器
  → 生成 AI 工作包
  → AI 提出实现与模型变化
  → 独立检查器判定并产生证据
  → 失败修复；未知升级；通过后记录与棘轮
```

需求变化、模型变化、代码变化和证据变化不是单向阶段。它们会互相使旧决定或证据失效；
每次变化都要写清触及的声明和要求重跑的检查。Assay 当前按清单显式登记的绑定执行，
不会自动推断完整语义影响面。

## 当前能力边界

- 已有：统一目录模型；Spec Ledger `init / expand / check`；Assay `run / map / check`；显式 `C→O` 来源链接；按义务 ID 追溯的版本化 JSONL 证据历史。
- 新增：`tools/prepare_work_package.py` 从单条已接受决定生成可交给 AI 的工作包并读取当前格式的历史证据；`tools/new-rust-project.ps1` 完成 Spec Ledger 初始化并安装模板。
- 尚无：自然语言目标自动变成已批准规格；Spec Ledger 到 Assay 的自动投影；自动生成 Quint、
  Verus 或 Capella 模型；对未声明性质的完整影响分析。
- 因此：AI 负责起草与转换，人负责语义裁决，工具负责各自明确范围内的拒绝与证据。
