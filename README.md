# assay

> 这台机器只做一件事：**说过的话必须兑现。兑现不了，不许通过。**

要把 Assay 用于一个新 Rust 项目，先看 [统一模型](UNIFIED_MODEL.md)、[WORKFLOW.md](WORKFLOW.md) 和
[Rust 项目模板](templates/rust-app/README.md)。它们规定从意图、架构与义务，到 AI
任务包和后端判定器的协作流程。

它由三样东西组成，按这个顺序长出：

| | 是什么 | 在哪 |
|---|---|---|
| **协议** | 什么算一条声明、什么算一次兑现 | [PROTOCOL.md](PROTOCOL.md) |
| **引擎** | 一个哑执行器：读清单 → 跑命令 → 追加证据事件 → 生成地图 → 比对棘轮 | [engine/](engine/)（[README](engine/README.md)、[依赖登记](engine/VENDOR.md)） |
| **清单** | 某个具体项目承认了什么、谁判的 | 每个目标仓自己的 `assay/manifest.toml` |

目标、决策、假设、义务、触发器与机械检查由同一仓库内的 Spec Ledger 工作流承载：根级
`ledger/` 与 `tools/spec.py` 管理可追溯的规格和判定；`assay/` 保存本仓自身的声明与证据。
新项目通过 `tools/new-rust-project.ps1` 获得独立账本工具和模板，不再依赖旁边单独检出的
Spec Ledger 仓库。

新 Rust 项目的端到端工作流见 [WORKFLOW.md](WORKFLOW.md)。初始化脚本复用 Spec Ledger，
`tools/prepare_work_package.py` 则从已接受的决定生成可交给 AI 的任务包。

可运行的 Rust 服务纵切与全流程验证命令见 [examples/README.md](examples/README.md)。

**引擎可丢弃，产物不可丢弃。** 删掉引擎只失去自动化，不失去知识。

证据历史以 `assay/evidence/*.jsonl` 为准，`.json` 是最新事件视图。工作包生成器读取新格式的 Assay 证据；Spec Ledger 的旧 YAML 状态只作为迁移期历史回退，不与新事件争夺权威。

## 实验编号 → 工具（协议不记录工具名）

协议和引擎里**不出现任何判定后端或项目的名字**（这是 `C-001`/`C-002`，各有一条会红的检查看着）。
所以修订记录里只有不透明的编号，映射放在这里——**在协议外面**。

| 编号 | 实验 | 买了什么 |
|---|---|---|
| `E1` | `tmp/verus-01/`（Rust 契约后端） | `trust_assumption` 字段：组合论证的前提无法机械化，必须显式登记 |
| `E2` | `tmp/quint-01/`（时序/状态机后端） | `scope` 字段与覆盖范围规则：一个名叫 `verify` 的检查器实际只覆盖 ≤25 步 |
| 狗粮 | 本仓自己（`assay/manifest.toml`） | `self-test` 能力、`red_command`、分歧规则 |

## 它现在能做什么

```
assay run   [--root <p>] [--stage <s>] [--check <id>] [--change <id>] [--certify]
assay map   [--root <p>]
assay check [--root <p>]
```

- `run` — 跑检查、写证据、报分歧、必要时**当场复现出生证明**、把兑现的检查纳入棘轮。
- `map` — 由清单机械生成单页地图（手改即红灯）。
- `check` — 清单自检 + 覆盖 + 出生证明三态 + 变更记录 + 棘轮削弱 + 地图新鲜度。**不需要跑任何检查。**

退出码：全绿 `0`／有红 `1`／清单本身有问题 `2`。

## 狗粮：它给自己写的清单

`assay/manifest.toml` 里的每一条声明，都是 **PROTOCOL.md 已经承诺的规则**。
即：这台机器声称自己会做的事，逐条配了一条会红的检查。

```
== 出生证明 ==
  🎓 可复现（有 `red_command`，机器能证明它红得了）：9 条
  ✅ 没有仅靠自述的出生证明
  ✅ 没有缺失出生证明的检查
```

**第一次跑就抓到了三处真东西**，都不是设计出来的：

1. **协议的最大自觉缺口。** §5 说出生证明"本协议最重要"，但它只是一个自述字符串——
   一段很像样的 `seen_red` 和一次真的注入，在文本上无法区分。
   → 由此有了 `red_command`（v0.4）：一条**期望非零退出**的命令。见 [PROTOCOL.md §5](PROTOCOL.md)。
2. **协议自己的零领域字符检查，抓到了协议自己的修订记录。**
   那两行写着"由实验 `verus-01`/`quint-01` 新增…"——它们点了名。
   → 协议改用不透明编号，映射搬到本文件。**这正是"当规则第一次挡住你自己"的时刻。**
3. **§3 自相矛盾**：标题写"协议只认这些词"，节末又写"新增能力不需要改协议"。
   一个不校验的表不可能同时是闸门。→ 改成"已知能力的登记"，并新增 `self-test`（v0.3）。

第 2 条与第 3 条是同一类东西：**规则的第一次真实运行，通常先挡住写规则的人。**

## 出生证明是怎么被机械复现的

让"档 4 会被拒"这条检查红，唯一的办法是**把引擎做坏**。
所以 `assay/selfcheck/inject/R-*.ps1` 会：复制 crate → 打一个必须**恰好命中一次**的字面量补丁 →
编译到共享 target 目录 → 用那个故意做坏的副本跑检查 → 要求它转红。

- 不碰工作树，不碰真引擎（也避开 Windows 对运行中 exe 的独占锁）。
- **注入点找不到 ⇒ 立刻失败**——注入器自己也有门禁。
- 退出码约定：**非零 = 证书成立**（"能失败"就是要证明的那件事）；
  **所有"没证明出来"的情况一律归 0**（检查没红 / 注入点失效 / 编译失败 / 内部报错）。
  **一个坏掉的见证者必须闭嘴，不能点头。**

## 边界（明确不做）

不建平台，不建中心模型，不做影响分析，不认识任何工具，**不判断分歧里谁对**。
引擎的每一个特性，都必须能说出是"哪个项目的哪一次真实摩擦"买来的。

项目工作流在引擎之上：Spec Ledger 管目的、决策、假设和义务；项目模板把已裁决的
工作整理成 AI 任务包；TLA+/Quint、Verus、MBSE 等工具只作为具体项目选择的检查命令。
当前尚无从 Spec Ledger 自动生成 Assay 清单或形式化模型的转换器；不要把人工确认的
工程语义伪装成可由引擎推导的事实。

本机 `D:\GitHub` 是按需检索的参考库，不是要求预先读完的教材。遇到具体设计问题时，
按 [工作流中的参考检索方法](WORKFLOW.md#按需借鉴参考项目) 搜索少量相关项目，读实现与测试，
再记录适用条件和本项目的决定。

详见 [PROTOCOL.md §8](PROTOCOL.md) 与 [engine/README.md](engine/README.md)。
